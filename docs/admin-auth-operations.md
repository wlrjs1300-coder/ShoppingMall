# 관리자 인증 및 권한 운영

관리자 API는 운영 환경에서 DB 기반 관리자 계정만 허용합니다. 공용 `ADMIN_CODE` 로그인은 운영에서 항상 차단되며 고객용 JWT를 관리자 API에 사용할 수 없습니다.

## 최초 최고 관리자 준비

1. 정상적인 회원가입 절차로 개인별 계정을 생성합니다.
2. 운영 DB 백업과 변경 승인을 확인합니다.
3. 서버 디렉터리에서 `npm run user:promote -- <아이디 또는 이메일>`을 실행합니다.
4. 해당 계정이 `super_admin`, 활성 상태로 준비됐는지 관리자 계정 목록에서 확인합니다.
5. 공용 자격증명을 공유하지 않고 개인 비밀번호 관리 정책을 적용합니다.

스크립트는 기본·데모 계정을 자동 생성하지 않습니다. 운영 배포 전 활성 `super_admin`이 최소 한 명인지 사람이 확인해야 합니다.

## 역할과 권한

- `super_admin`: 모든 운영 권한과 관리자 계정 관리
- `operations`: 주문·생산·재고·발주 운영 및 결제 조회
- `finance`: 주문·결제 조회, 결제 재조정 및 취소
- `viewer`: 주문·재고·발주·결제·활동 로그 읽기

서버의 permission 검사가 최종 기준입니다. UI에서 버튼이 보이지 않는 것은 보안 경계가 아닙니다.

## 계정 변경과 퇴사자 회수

- 역할 변경과 비활성화는 `super_admin`만 수행합니다.
- 변경 시 `token_version`이 증가하여 기존 관리자 토큰이 즉시 무효화됩니다.
- 비밀번호 변경과 강제 세션 만료도 `token_version`을 증가시킵니다.
- 퇴사자는 먼저 계정을 비활성화하고 감사 로그에서 거부 기록을 확인합니다.
- 마지막 활성 `super_admin`은 비활성화하거나 강등할 수 없습니다.
- 현재 로그인한 자신의 계정은 실수로 비활성화할 수 없습니다.

## 긴급 접근과 복구

운영에서 legacy `ADMIN_CODE`를 켜는 긴급 우회는 제공하지 않습니다. 관리자 접근을 잃은 경우 승인된 DB 운영 절차와 백업을 확인한 뒤, 개인 회원 계정에 `user:promote`를 적용합니다. 복구 후 즉시 관련 계정, 역할, 세션과 감사 로그를 검토하세요.

## 감사와 모니터링

로그인 성공·실패, 비활성 계정 시도, 권한 거부, 역할 변경, 비활성화와 세션 회수 이벤트를 `activity_logs`에서 확인합니다. 비밀번호, hash, JWT, Authorization 헤더, `ADMIN_CODE`는 기록하지 않습니다. 반복 실패와 권한 거부는 외부 로그 수집 시스템에서 경보로 연결하는 것을 권장합니다.

## 환경 설정

운영에는 안전한 `JWT_SECRET`, `ADMIN_JWT_ISSUER`, `ADMIN_JWT_AUDIENCE`, `ADMIN_TOKEN_TTL`, `ADMIN_LOGIN_RATE_MAX`, `ADMIN_LOGIN_RATE_WINDOW_MS`가 필요합니다. 실제 비밀값이나 계정 정보를 문서와 저장소에 기록하지 마세요.
