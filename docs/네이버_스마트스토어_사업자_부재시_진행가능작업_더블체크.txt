네이버 스마트스토어 서비스 연결
사업자 본인 없이 진행 가능한 작업 더블체크 목록

작성일: 2026-08-09
검토 대상: 따뜻한 떡집 ShoppingMall 저장소
검토 기준: 현재 프로젝트 코드 + 네이버 커머스API 공식 문서

============================================================
1. 최종 결론
============================================================

사업자 본인이 없어도 다음 상태까지는 개발자가 준비할 수 있다.

  “네이버 커머스API 인증정보와 실제 스마트스토어 상품번호만 전달받으면,
   제한된 읽기 테스트부터 안전하게 시작할 수 있는 상태”

다만 현재 프로젝트가 이미 네이버 스마트스토어와 완전히 연결된 상태는 아니다.
현재 구현은 아래 범위까지 확인된다.

[현재 구현됨]
- 네이버 OAuth2 Client Credentials 인증 클라이언트
- bcrypt 기반 전자서명 생성
- 토큰 발급 및 만료 전 재사용
- 인증 실패, 호출 제한, 서버 오류에 대한 제한적 재시도
- 네이버 상품 검색 및 단건 조회
- 내부 상품과 네이버 채널 상품 매핑 저장·조회·검증
- 네이버 변경 상품주문 조회
- 최대 300건 단위 상품주문 상세 조회
- 주문 수집 중복 방지, 커서, 실행 잠금, 부분 실패 기록
- 네이버 주문을 별도 수집 테이블에 저장
- 주문 개인정보 암호화 및 마스킹 기반
- 2분 기본 주기의 자동 수집 스케줄러
- Render 환경변수 자리와 기본 비활성화 설정
- 관련 단위·통합 테스트

[현재 미구현 또는 운영 전 추가 필요]
- 네이버 연동 전용 관리자 화면
- 네이버 수집 주문을 기존 주문관리 주문으로 자동 생성하는 변환 단계
- 네이버 상품 신규 등록 API 연동
- 네이버 상품 수정 API 연동
- 가격 자동 동기화
- 완제품 재고 모델 및 재고 자동 동기화
- 옵션 상품 매핑
- 발주 확인·발송 처리 API 쓰기 연동
- 취소·반품·교환 자동 처리
- 실제 인증정보를 사용한 운영 연결 검증
- 실제 스마트스토어 상품과의 매핑 검증
- 실제 테스트 주문 전체 흐름 검증

따라서 사업자 본인을 기다리는 동안에는 PWA 관리자 디자인보다
네이버 연동의 데이터·운영 기반을 먼저 완성하는 것이 맞다.

============================================================
2. 공식 문서 재확인 결과
============================================================

1) 네이버 커머스API는 서버 간 연동용 API다.
- OAuth 2.0 Client Credentials 방식을 사용한다.
- API 호출 시 Bearer 토큰을 사용한다.
- 일반 사용자가 네이버 아이디로 로그인하는 소셜 로그인과는 별개다.

2) 토큰 발급에는 다음 정보가 필요하다.
- client_id
- client_secret으로 생성한 전자서명
- millisecond 단위 timestamp
- grant_type=client_credentials
- type=SELF 또는 SELLER
- SELLER 방식이면 account_id 필요

3) 인증 토큰 유효 시간은 공식 문서 기준 3시간(10,800초)이다.
- 남은 유효 시간이 30분 이상이면 기존 토큰이 반환될 수 있다.
- 30분 미만이면 새 토큰이 발급된다.

4) 애플리케이션에 필요한 API 그룹 권한이 있어야 한다.
- 커머스API는 OAuth scope 문자열을 별도로 제공하지 않는다.
- 커머스API센터에서 애플리케이션 등록·수정 시 API 그룹을 선택한다.

5) 허용되지 않은 호출 IP에서는 403 GW.IP_NOT_ALLOWED가 발생한다.
- 실제 배포 서버의 외부 호출 IP를 확인해야 한다.
- 커머스API센터에 정확한 호출 IP가 등록돼야 한다.

6) 호출량 제한은 고정된 하나의 숫자가 아니다.
- API 및 애플리케이션 단위 rate limit이 적용된다.
- 429 GW.RATE_LIMIT 또는 GW.QUOTA_LIMIT이 발생할 수 있다.
- 응답의 RateLimit·Quota 관련 헤더를 수집해 운영값을 조정해야 한다.

7) 변경 상품주문 조회는 변경 일시 기준이다.
- 한 번에 최대 300건 또는 요청한 limitCount만큼 반환한다.
- 300건을 초과하면 moreFrom과 moreSequence로 이어서 조회해야 한다.

8) 상품 대표 이미지는 필수다.
- 공식 상품 구조는 대표 이미지 1000×1000픽셀을 권장한다.
- 추가 이미지는 최대 9개까지 지원한다.
- 상품 API에 전달하는 이미지 URL은 네이버 이미지 업로드 API 결과여야 한다.

9) 상품 판매 상태에는 판매 중, 품절, 판매 중지 등이 별도로 존재한다.
- SALE, OUTOFSTOCK, SUSPENSION 등을 내부 판매 상태와 구분해서 매핑해야 한다.

10) 실제 운영 스토어에서의 API 테스트는 보수적으로 진행해야 한다.
- 최초 연결은 읽기 전용으로 시작한다.
- 상품 수정, 재고 변경, 발송 처리 같은 쓰기 API는 별도 승인 후 활성화한다.

3. 지금 바로 진행 가능한 작업
============================================================

[우선순위 1] 네이버 판매 대상 메뉴 확정

사업자 계정이나 API 인증정보 없이 진행 가능하다.

할 일:
- 전체 내부 메뉴 목록 추출
- 판매 중인 메뉴만 후보로 분류
- 상담 주문 상품 제외
- 가격이 없는 상품 제외
- 대표 이미지가 없는 상품 제외
- 원산지 정보가 불완전한 상품 표시
- 계절 상품 표시
- 팩 단위와 말 단위 판매 구조 분리
- 네이버에서 배송 가능한 상품과 매장 전용 상품 분리
- 판매 중지 시 네이버에서도 중지해야 하는 상품 표시

현재 코드의 제한:
- purchaseType=direct인 상품만 매핑 가능
- status=active인 상품만 매핑 가능
- 가격이 유효한 상품만 매핑 가능
- 네이버 옵션 상품은 매핑 불가

권장 초기 정책:
- 1차 오픈은 옵션 없는 단일 상품만 연결
- 팩 상품과 말 단위 상품은 별도 네이버 상품으로 등록하는 방안 우선 검토
- 상담 주문 상품은 네이버 자동 연동 대상에서 제외

완료 기준:
- 각 내부 메뉴에 네이버 판매 여부가 명시됨
- 판매 단위와 가격이 명확함
- 옵션이 필요한 상품이 별도로 분류됨

[우선순위 2] 스마트스토어 상품 등록 자료 패키지 작성

사업자 본인 없이 현재 메뉴 데이터와 제공받은 사업 정보를 이용해 준비 가능하다.

상품별 준비 항목:
- 내부 상품 ID
- 판매자 관리 코드 후보
- 네이버용 상품명
- 카테고리 후보
- 판매가
- 초기 재고 후보
- 판매 단위
- 대표 이미지
- 추가 이미지
- 상세 설명
- 원재료·원산지
- 보관·해동 방법
- 배송 안내
- 교환·반품 안내
- 검색 태그 후보
- 판매 상태

추가 검증:
- 대표 이미지 1000×1000 권장 규격 충족 여부
- 이미지 용량과 포맷
- 추가 이미지 9개 이하
- 상세 설명 내 깨진 링크·로컬 경로 제거
- 과장 광고 또는 근거 없는 표현 확인
- 가격, 중량, 상품명 상호 일치 확인
- 원산지 표기 누락 확인

완료 기준:
- 네이버 상품 등록 화면에 복사·업로드할 수 있는 자료가 상품별로 준비됨
- 사업자가 최종 확인해야 할 항목만 별도로 표시됨

[우선순위 3] 상품 등록 전 자동 검증 도구 구현

인증정보 없이 구현·테스트 가능하다.

검증 항목:
- 상품 ID 누락 및 중복
- 판매자 관리 코드 중복
- 상품명 누락 및 길이 초과
- 가격 누락 또는 0원
- 대표 이미지 누락
- 로컬에서만 접근 가능한 이미지 경로
- 상세 설명 누락
- 원산지 누락
- 상담 전용 상품 포함
- 판매 중지 상품 포함
- 옵션 필요 상품 포함
- 팩·반말·한말 가격 불일치
- 배송·교환·반품 정보 누락
- 금지·제한 태그 후보

완료 기준:
- 네이버 등록 후보 전체에 대해 통과·주의·차단 결과가 출력됨
- 차단 사유를 상품별로 확인할 수 있음

[우선순위 4] 네이버 연동 관리자 화면 구현

실제 API 대신 모의 응답으로 개발 가능하다.
PWA 관리자 전체 디자인 작업과 달리 실제 서비스 연결에 직접 필요한 화면만 만든다.

필수 화면:
1. 연결 상태
   - 연동 비활성/활성
   - 인증 확인 상태
   - 마지막 성공 시각
   - 마지막 실패 코드

2. 상품 매핑
   - 내부 메뉴 선택
   - 네이버 채널 상품번호 입력
   - 네이버 상품 검색
   - 상품명·상태·판매자 코드 비교
   - 연결, 비활성화, 재검증
   - 미매핑·충돌·옵션 미지원 표시

3. 주문 수집 현황
   - 마지막 수집 시각
   - 수집 주문 수
   - 실패 주문 수
   - 미매핑 주문 수
   - 수동 수집
   - 실패 건 재조회

4. 안전 설정
   - 자동 수집 활성화 여부
   - 최초 조회 시간
   - 폴링 주기
   - 쓰기 API 비활성 상태 표시

권한:
- 조회: sales_channels:read
- 변경·수동 동기화: sales_channels:manage

완료 기준:
- 실제 키 없이 모의 데이터로 전체 UI와 권한 검증 완료
- 인증정보 수령 후 API만 교체하면 동작 가능한 구조

[우선순위 5] 네이버 주문을 내부 주문관리로 변환하는 단계 구현

중요:
현재 코드는 네이버 주문을 sales_channel_order_imports 계열 테이블에 저장하지만,
기존 orders와 order_items에 자동 생성하지 않는다.

사업자 본인 없이 구현 가능한 항목:
- external orderId와 productOrderId 중복 방지
- 네이버 주문 1건을 내부 주문 1건으로 변환
- 상품주문을 내부 order_items로 변환
- 상품 매핑이 없는 주문은 자동 생성하지 않고 수동 검토로 분류
- 네이버페이 결제를 자체몰 Toss 결제와 분리
- 할인, 배송비, 결제 금액 snapshot 저장
- 주문 상태 변환
- 취소·반품·교환 상태 별도 보존
- 변환 실패 시 원본 수집 주문 유지
- 관리자가 승인한 주문만 내부 주문으로 전환하는 안전 모드

필수 상태 매핑 후보:
- PAYMENT_WAITING → 결제대기
- PAYED → 접수대기
- DELIVERING → 배송중
- DELIVERED → 배송완료
- PURCHASE_DECIDED → 구매확정
- CANCELED → 취소
- RETURNED → 반품
- EXCHANGED → 교환
- CANCELED_BY_NOPAYMENT → 미결제취소

주의:
- 네이버 클레임은 상품주문 단위이므로 주문 전체 상태에 강제로 합치면 안 됨
- 부분 취소·부분 반품·부분 교환은 order item 단위 모델이 필요함
- 외부 네이버페이 결제를 Toss 승인·취소 로직으로 보내면 안 됨

권장 1차 범위:
- 읽기 전용 수집
- 관리자 확인
- 내부 주문 생성
- 상태 표시
- 네이버에 상태를 다시 쓰는 동작은 제외

완료 기준:
- 동일 네이버 주문을 반복 수집해도 내부 주문이 중복 생성되지 않음
- 미매핑 상품 주문은 자동 처리되지 않음
- 네이버페이와 Toss 결제가 혼합되지 않음

[우선순위 6] 모의 네이버 주문 전체 흐름 테스트

인증정보 없이 공식 응답 형식의 fixture로 실행 가능하다.

필수 테스트:
- 신규 주문 최초 수집
- 같은 주문 반복 수집
- 주문 1건에 여러 상품주문 포함
- 300건 초과 continuation 처리
- 상품 매핑 누락
- 잘못된 네이버 상품번호
- 결제대기에서 결제완료로 변경
- 배송 상태 변경
- 취소 요청
- 부분 취소
- 반품 요청
- 교환 요청
- API 401 인증 실패
- API 403 권한 또는 IP 실패
- API 429 rate limit
- API 500·503·504
- 응답 일부 누락
- 중간 페이지 실패 후 재시도
- 서버 재시작 후 커서 복구
- 동시에 두 번 실행했을 때 중복 방지
- 개인정보 암호화·복호화
- 로그에 이름·전화번호·주소가 평문으로 남지 않는지 검사

완료 기준:
- 실제 네이버 호출 없이 전체 테스트 통과
- 재시도 불가능 오류와 재시도 가능 오류가 구분됨
- 중복 내부 주문 생성 0건

[우선순위 7] Render 운영 환경 사전 준비

실제 Client ID와 Secret 없이 준비 가능하다.

현재 render.yaml에 준비된 항목:
- NAVER_COMMERCE_SYNC_ENABLED=false
- NAVER_COMMERCE_CLIENT_ID
- NAVER_COMMERCE_CLIENT_SECRET
- NAVER_COMMERCE_AUTH_TYPE=SELF
- NAVER_COMMERCE_ACCOUNT_ID
- NAVER_COMMERCE_API_BASE_URL=https://api.commerce.naver.com/external
- NAVER_COMMERCE_REQUEST_TIMEOUT_MS=10000
- NAVER_ORDER_IMPORT_ENABLED=false
- NAVER_ORDER_POLL_INTERVAL_MS=120000
- NAVER_ORDER_INITIAL_LOOKBACK_MINUTES=10
- NAVER_ORDER_PII_KEY
- NAVER_ORDER_PII_KEY_VERSION=v1

지금 가능한 작업:
- 운영용 32바이트 주문 개인정보 암호화 키 생성 절차 준비
- 환경변수 입력 체크리스트 작성
- Client Secret 로그 출력 차단 확인
- production API base URL allowlist 확인
- 서버 시작 전 설정 검증 확인
- 동기화 비활성 상태 배포 확인
- DB migration 및 백업·복구 확인
- 실패 시 feature flag를 false로 내리는 절차 작성
- 배포 서버의 고정 외부 호출 IP 제공 가능 여부 확인

중요:
- 현재 APP_ENV=staging에서는 네이버 연동 활성화를 의도적으로 차단한다.
- 실제 호출 검증은 별도 production-like 환경 또는 승인된 운영 환경에서 진행해야 한다.
- 인증정보가 없을 때 두 활성화 값은 반드시 false로 유지한다.

완료 기준:
- 비밀값 없이 서버가 정상 배포됨
- 키가 비어 있으면 연동이 활성화되지 않음
- 비밀값이 Git과 로그에 남지 않음

------------------------------------------------------------

[우선순위 8] 초기 주문 수집 정책 수정·확정

현재 코드 확인 결과:
- 자동 폴링 기본 주기: 120초
- 허용 폴링 범위: 60초~180초
- 자동 폴러 최초 lookback 기본값: 10분
- 수동 initialLastChangedFrom 검증 범위: 현재 시점 기준 최대 24시간

중요 정정:
- 설계 문서에는 초기 30일 후보가 있지만 현재 구현은 24시간보다 오래된 시작 시각을 거부한다.
- 따라서 30일 과거 주문을 한 번에 초기 수집하는 기능은 현재 사용할 수 없다.

지금 결정·구현 가능한 선택지:
A. 서비스 연결 시점 이후 주문만 수집
B. 최근 24시간만 초기 수집
C. 과거 주문 backfill 전용 도구를 별도 구현

권장:
- 1차 오픈은 B 또는 연결 시점 이후 수집
- 과거 주문 backfill은 실제 주문량 확인 후 별도 승인

------------------------------------------------------------

[우선순위 9] 모니터링과 운영 안전장치

사업자 본인 없이 구현 가능하다.

필수 모니터링:
- 마지막 인증 성공 시각
- 마지막 주문 수집 성공 시각
- 연속 실패 횟수
- 수집 지연 시간
- 미매핑 상품주문 수
- 부분 실패 수
- 재시도 대기 수
- 401 GW.AUTHN
- 403 GW.IP_NOT_ALLOWED
- 429 GW.RATE_LIMIT
- 429 GW.QUOTA_LIMIT
- 5xx·timeout
- 네이버 Trace ID

보안 원칙:
- Trace ID는 저장 가능
- Client ID·Secret·access token은 로그 금지
- 주문 전체 응답 body 로그 금지
- 고객 이름·전화번호·주소 평문 로그 금지

알림 후보:
- 10분 이상 주문 수집 성공 없음
- 인증 연속 실패
- 미매핑 주문 발생
- 부분 실패 누적
- 알 수 없는 상태 코드 발견
- 개인정보 평문 로그 탐지

------------------------------------------------------------

[우선순위 10] 운영 실행·복구 문서 작성

사업자 본인 없이 작성 가능하다.

문서에 포함할 내용:
- 인증정보를 안전하게 전달받는 방법
- Render 환경변수 입력 위치
- 실제 비밀값을 GitHub에 올리지 않는 방법
- 인증정보 설정 전 비활성 상태 확인
- 첫 토큰 발급 테스트
- 판매자 계정 정보 읽기 테스트
- 상품 1개 조회 테스트
- 상품 1개 매핑 테스트
- 최근 10분 주문 조회 테스트
- 자동 수집 활성화 순서
- 실패 시 즉시 비활성화 순서
- Client Secret 교체 절차
- 개인정보 암호화 키 교체 절차
- DB 백업과 복구 절차
- 네이버 장애 시 수동 운영 절차

============================================================
4. 사업자가 한 번 설정한 뒤 인증정보만 전달하면 진행 가능한 작업
============================================================

아래 작업은 실행 순간에 사업자 본인이 옆에 있을 필요는 없지만,
사업자가 먼저 커머스API센터 등록과 권한 설정을 완료해야 한다.

1. Render에 Client ID와 Client Secret 입력
2. SELF 또는 SELLER 인증 방식 최종 설정
3. SELLER 방식이면 account_id 입력
4. 네이버 토큰 발급 확인
5. 판매자 계정 정보 읽기
6. API 권한 그룹 정상 여부 확인
7. 허용 IP 정상 여부 확인
8. 네이버 상품 목록 읽기
9. 내부 메뉴와 실제 채널 상품번호 매핑
10. 최근 변경 주문 제한 조회
11. 수집 데이터 암호화 저장 확인
12. 실제 테스트 주문 1건 수집
13. 동일 주문 재수집 중복 방지 확인
14. 자동 주문 수집 활성화
15. 모니터링과 실패 알림 확인

보안 주의:
- Client Secret을 카카오톡, 이메일 본문, GitHub Issue, 코드, 문서에 기록하지 않는다.
- 가능하면 사업자가 Render 환경변수에 직접 입력한다.
- 개발자는 Secret 원문을 보관하지 않는다.

============================================================
5. 사업자 본인이 반드시 해야 하므로 이번 목록에서 제외할 작업
============================================================

다음은 개발자가 대신 진행한다고 가정하면 안 된다.

- 스마트스토어 판매자 계정 개설
- 본인 인증
- 사업자등록 정보 제출 및 심사 대응
- 통신판매업 등 필요한 사업 신고 확인
- 정산 계좌 등록·인증
- 네이버 약관 동의
- 커머스API센터 가입 또는 판매자 연동 승인
- 애플리케이션 등록의 최종 승인
- 필요한 API 그룹 선택·승인
- 호출 IP 등록 승인
- 판매자 ID·UID 또는 account_id 확인
- 출고지·반품지·교환지 최종 등록 및 확인
- 배송비·반품비 최종 사업 정책 승인
- 실제 판매 상품, 가격, 재고, 판매 시작에 대한 최종 승인
- Client ID·Client Secret 발급 및 안전한 입력

============================================================
6. 지금 진행하면 안 되는 작업
============================================================

사업자 계정과 실제 데이터 검증 전에는 아래 기능을 활성화하지 않는다.

- NAVER_COMMERCE_SYNC_ENABLED=true
- NAVER_ORDER_IMPORT_ENABLED=true
- 실제 상품 가격 자동 수정
- 실제 상품 재고 자동 수정
- 실제 상품 판매 상태 자동 변경
- 발주 확인 자동 전송
- 발송 처리 자동 전송
- 취소 자동 승인
- 반품 자동 승인
- 교환 자동 승인
- 네이버 주문을 검토 없이 기존 주문으로 자동 생성
- 과거 주문 대량 backfill
- 운영 스토어에서 반복적인 쓰기 API 테스트

============================================================

============================================================

1단계. 네이버 판매 대상 메뉴 확정

8. 가장 먼저 진행할 작업
============================================================

현재 가장 먼저 할 작업은 아래 두 가지다.

1. 네이버 판매 대상 메뉴와 판매 단위 확정
2. 네이버 상품 매핑·주문 수집 현황 관리자 화면 구현

이유:
- 사업자 계정이 없어도 완료할 수 있다.
- 실제 상품번호와 인증정보를 받은 뒤 연결 시간이 크게 줄어든다.
- 현재 코드의 가장 큰 공백인 운영 화면을 채운다.
- 옵션 상품, 상담 상품, 가격 누락 상품을 연결 전에 차단할 수 있다.

그 다음에는 현재 별도 수집 테이블에 저장되는 네이버 주문을
기존 주문관리로 안전하게 가져오는 변환 단계를 구현해야 한다.

10. 검토 메모
============================================================

- 공식 문서는 2026-08-09 확인 시 2.84.0 릴리스가 노출되고 있었다.
- API 필드와 상태 코드는 실제 연결 직전 최신 문서로 다시 확인해야 한다.
- 네이버 호출 제한 값은 고정값으로 가정하지 않고 응답 헤더를 기준으로 운영해야 한다.
- 이 파일은 네이버 스마트스토어 연결에 한정하며 PWA 관리자 디자인,
  자체몰 Toss 결제, 문자·이메일, 사업자 정보 페이지 작업은 포함하지 않는다.
